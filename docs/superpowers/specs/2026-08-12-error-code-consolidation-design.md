# 에러코드 페이지 통합 설계 — 애드센스 thin content 대응 1순위

작성일: 2026-08-12
대상: `src/lib/error-codes.ts`, `/error-codes/*` 라우트, 제품 상세의 에러코드 섹션

## 배경

살림랩이 구글 애드센스 심사에서 **"가치가 별로 없는 콘텐츠"**로 거절됐다. 거절 통지가 링크한 자료는 최소 콘텐츠 요건, 고유 콘텐츠 확인, 내용이 빈약한 콘텐츠에 대한 웹마스터 품질 가이드라인이다.

원인은 데이터로 분명하다. 빌드된 383개 페이지의 본문 길이를 재보면:

| 페이지 유형 | 개수 | 본문 길이 중앙값 |
|---|---|---|
| 제품 | 74 | 5,300자 |
| 카테고리 | 12 | 6,004자 |
| **에러코드 상세** | **254** | **618자** |
| 브랜드 | 17 | 562자 |
| 성분 사전 | 3 | 944자 |

**1,200자 미만이 373개 중 279개(75%)다.** 그리고 위 618자는 내비게이션과 푸터를 포함한 값이다. 에러코드 상세 페이지의 고유 본문만 재면 **중앙값 185자, 최소 19자**이고, 140개가 200자 미만이다. 254개 중 149개는 발생 제품이 하나뿐이다.

실제 페이지 전문은 이 정도다:

> 원인: 온도센서 불량 또는 연결 불량 / 해결: 전원 끄고 10분 후 재가동. 반복 시 서비스센터 연락

이런 페이지가 사이트의 70%를 차지한다. 자동 생성된 얇은 템플릿을 대량으로 찍어낸 구조로 읽힌다.

**Search Console 기준 이 페이지들의 유입은 거의 없다.** 따라서 통합은 가치를 파괴하는 일이 아니라 부채를 제거하는 일이다.

## 결정 사항

- **통합 단위는 브랜드.** 254개 코드 페이지를 없애고 기존 `/error-codes/[brand]` 허브 13개에 내용을 인라인한다.
- **허브가 원본, 제품 페이지는 요약 + 링크.** 중복을 만들지 않는다.
- **리다이렉트는 브랜드 허브까지만.** 코드 단위 앵커는 포기한다.
- **브랜드 페이지(`/brand/*`) 보강은 다음 사이클.** 성격이 다르고, 이번 것만으로도 파일 8개를 손댄다.

### 왜 브랜드 단위인가

세 후보를 실측했다.

| 방식 | 페이지 수 | 고유 본문 | 500자 미만 |
|---|---|---|---|
| 현재 (브랜드×코드) | 254 | 중앙값 185자 | 다수 |
| **브랜드** | **13** | 1,346 ~ 12,540자 | **0개** |
| 브랜드×카테고리 | 38 | 중앙값 1,420자 | 4개 |

브랜드 단위를 택한 이유는 셋이다.

1. **얇은 페이지가 0개가 된다.** 이번 목적이 정확히 그것이다. 브랜드×카테고리는 38개 중 4개(LG 공기청정기 216자, LG 선풍기 224자 등)가 여전히 얇게 남는다.
2. **새 라우트가 필요 없다.** `/error-codes/[brand]` 허브가 이미 13개 있고 지금은 목록만 있어 562자다. 내용을 옮기면 그대로 두꺼워진다.
3. **삼성 12,540자는 문제가 아니다.** 긴 페이지는 thin content가 아니다. 페이지 안에서 카테고리별 섹션과 앵커 목차로 탐색하면 된다.

제품이 늘어 브랜드 페이지가 20,000자를 넘으면 그때 브랜드×카테고리로 쪼개는 것이 자연스럽다. 지금은 이르다.

## 목표 구조

```
삼성 에러코드                          ← h1
[에어컨 12] [세탁기 9] [냉장고 15] …    ← 카테고리 앵커 목차

## 에어컨                              ← h2
  E1  주의                             ← h3, id="air-conditioner-e1"
      실내 온도센서 이상
      원인: 온도센서 불량 또는 연결 불량
      해결: 전원 끄고 10분 후 재가동…
      나오는 제품: 비스포크 윈드프리 AF25A9970 · 윈드프리 벽걸이 AR07A9170
## 세탁기
  …
```

### 왜 카테고리로 나누나

**같은 코드가 카테고리마다 다른 의미다.** 삼성 E1은 에어컨에서 "실내 온도센서 이상", 제습기에서 "수위 센서 이상"이다. 현재 코드 상세 페이지는 둘을 한 페이지에 섞지만, 독자는 자기 제품의 카테고리를 알고 온다. 카테고리로 묶으면 검색 의도와 맞고 페이지 안에서 바로 찾힌다.

## 데이터 레이어

`src/lib/error-codes.ts`에 조회 함수를 추가한다.

```ts
export type BrandCategoryCodes = {
  category: ApplianceCategory;
  entries: {
    code: string;
    codeSlug: string;
    severity: ErrorCode['severity'];
    description: string;
    cause: string;
    solution: string;
    products: { slug: string; name: string }[];
  }[];
};

export function getBrandErrorCodes(brand: string): BrandCategoryCodes[];
```

### 중복 제거 키 — 정보 손실 방지

같은 브랜드·카테고리·코드가 제품 여럿에 걸릴 때, 보통은 설명·원인·해결이 같아서 제품만 합치면 된다. 그런데 **본문이 다를 수도 있다.** 첫 번째만 남기면 정보가 조용히 사라진다.

따라서 묶는 키는 **`코드 + 카테고리 + 본문(description·cause·solution)`**이다. 본문이 같으면 제품이 합쳐지고, 다르면 항목이 따로 남는다. 정보 손실이 구조적으로 불가능해진다.

**반환 순서는 결정적이어야 한다** — 정적 생성이라 순서가 흔들리면 빌드마다 HTML이 달라진다. 카테고리는 `CATEGORY_SLUGS`의 선언 순서, `entries`는 코드 문자열 오름차순, `products`는 카탈로그 등장 순으로 고정한다.

### 앵커 id 충돌 규칙

본문이 다르면 항목이 따로 남는다는 규칙 때문에, **같은 카테고리에 같은 코드가 두 항목으로 존재할 수 있다.** 그러면 `{categorySlug}-{codeSlug}` id가 중복되어 HTML이 깨진다.

외부에서 `errorCodeAnchor(brand, category, code)`가 중복 여부를 모른 채 id를 만들어야 하므로, 규칙은 이렇다: **같은 (카테고리, 코드)의 첫 항목이 깨끗한 id를 갖고, 이후 항목은 `-2`, `-3`을 붙인다.** 외부 링크는 깨끗한 id를 가리키고 첫 항목에 착지한다.

id 유일성은 테스트로 강제한다 — 13개 브랜드 전부에 대해 생성된 id 집합에 중복이 없어야 한다.

### 기존 함수 정리

- `errorCodeHref(brand, code)` → `errorCodeAnchor(brand, category, code)`, 반환값은 `/error-codes/{brand}#{categorySlug}-{codeSlug}`. 카테고리 ASCII 슬러그는 `category-config.ts`의 `CATEGORY_SLUGS`를 쓴다.
- `getAllErrorCodeParams()`는 코드 페이지가 사라지면 브랜드 목록 추출 용도로만 남아 이름이 거짓이 된다. `getErrorCodeBrands(): string[]`으로 바꾼다.
- `slugifyCode`는 앵커 생성에 계속 필요하므로 유지한다.

## 제품 페이지의 에러코드 섹션

전문 대신 **코드명 + 증상 한 줄 + 허브 앵커 링크**만 남긴다. 원인·해결은 허브에만 둔다.

```
에러코드 (구매 후 참고)
  E1  실내 온도센서 이상 →
  E2  실외기 통신 이상   →
  삼성 에러코드 전체 보기 →
```

**길이 영향은 안전하다.** 제품당 에러코드 본문은 중앙값 843자, 최대 1,714자다. 그런데 가장 짧은 제품 페이지 5개(3,403~3,836자)는 전부 비가전(무선이어폰·TV)이고 **에러코드가 없어 잃을 것이 없다.** 에러코드를 가진 가전은 전부 3,836자 이상이므로 최악의 경우에도 2,100자 이상 남는다.

## 리다이렉트

Cloudflare `_redirects`는 플레이스홀더를 지원하고, `wrangler.jsonc`가 `out/` 안의 규칙이 적용된다고 명시하고 있다. 254줄을 나열하는 대신 한 줄이면 된다.

```
/error-codes/:brand/:code  /error-codes/:brand  301
```

`public/_redirects`에 두면 Next가 `out/`으로 복사한다. 생성 스크립트가 필요 없고 데이터와 어긋날 여지도 없다.

### 앵커까지 보내지 않는 이유

같은 코드가 카테고리마다 다른 의미라 앵커가 코드 단위로 유일하지 않다. 삼성 E1은 에어컨과 제습기에 각각 있어 `id="e1"` 하나로는 HTML이 깨진다. 유입이 거의 없는 상황에서 리다이렉트의 목적은 크롤 에러 방지이지 UX 보존이 아니므로, 브랜드 허브 최상단에 떨어뜨리는 것으로 충분하다.

**사이트 내부 링크는 다르다.** 제품 상세와 에러코드 인덱스는 그 제품의 카테고리를 알기 때문에 `#{categorySlug}-{codeSlug}`로 정확히 보낼 수 있다.

### 배포해봐야 확인되는 것

- `wrangler.jsonc`의 `html_handling: "auto-trailing-slash"`와 상호작용 — `/error-codes/Samsung/e1/`도 규칙에 걸리는가
- `not_found_handling: "404-page"`보다 `_redirects`가 먼저 평가되는가

둘 다 배포 후 실제 요청으로 확인한다.

## 구조화 데이터

브랜드 허브의 `ItemList`는 사라질 상세 페이지 URL을 가리킨다. 페이지가 목록이 아니라 완결된 문서가 되므로 **`ItemList`를 제거하고 `BreadcrumbList`만 남긴다.**

## 검증

1. `npm run lint` → `npx tsc --noEmit` → `npm test` → `npm run build`
2. **얇은 페이지 제거 확인** — 빌드 후 `/error-codes/*` 브랜드 허브 13개가 전부 1,200자 이상
3. **정보 손실 없음 전수 대조** — 변경 전 데이터에서 `(브랜드, 카테고리, 코드, 본문)` 조합을 전부 뽑아두고, 변경 후 빌드된 HTML에서 같은 집합이 나오는지 확인. **이것이 이 작업의 핵심 게이트다.** 254개를 지우면서 코드 하나라도 증발하면 이 작업은 콘텐츠를 줄인 것이 된다.
4. **중복 제거 키 검증** — 본문이 다른 항목을 합치지 않는지 합성 픽스처 테스트. 테스트가 실제로 실패하는지 고의 파괴로 확인한다.
5. **회귀** — 제품 74개·카테고리 12개 페이지 유지, 사이트맵에 254개 코드 URL 부재
6. **배포 후** — `/error-codes/Samsung/e1`과 `/error-codes/Samsung/e1/` 둘 다 301 응답 확인

## 예상 결과

383페이지 → 129페이지. 1,200자 미만 페이지는 279개(75%)에서 **약 26개(20%)**로 줄어든다.

내역은 `/brand/*` 15개, 성분 사전 3개(본문 13개를 채우면 해소), 홈·about·compare·contact·terms·404 등 유틸리티 8개다. **남는 얇은 페이지의 최대 덩어리는 `/brand/*` 15개**이며, 이것이 다음 사이클의 대상이다.

## 다음 사이클

**`/brand/*` 15개 보강.** 지금 제품 목록만 있어 562자다. 이번 작업이 끝나면 이것이 남은 얇은 페이지의 대부분이 된다. 브랜드 소개·라인업 특징·해당 브랜드 에러코드 요약 등 콘텐츠 보강이며, 이번의 구조 재편과는 성격이 다르다.

그다음은 **리뷰 재구성**이다. 리뷰 329개 중 출처가 있는 것은 24개(7%)이고, 나머지는 사용자 페르소나와 별점을 단 형식으로 제시된다. 푸터에 "편집팀의 종합 평가이며 실제 사용자 후기가 아닙니다"라는 고지가 있지만 본문만 보면 사용자 후기로 읽힌다. 거절 사유가 링크한 "고유 콘텐츠와 우수한 사용자 환경"이 이 축이며, thin content보다 정책 위반에 가까운 문제일 수 있다.

## 범위 밖

- `/brand/*` 보강, 리뷰 재구성, 성분 사전 본문 13개 — 각자의 사이클.
- 에러코드 본문 자체의 품질 개선 — 이번은 구조 재편이지 콘텐츠 집필이 아니다.
- `ads.txt` — 404이지만 승인 후 문제이지 거절 사유가 아니다.
