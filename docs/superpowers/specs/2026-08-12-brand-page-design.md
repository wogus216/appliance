# 브랜드 페이지 보강 설계 — 애드센스 thin content 대응 2순위

작성일: 2026-08-12
대상: `src/app/brand/[brand]/page.tsx` 및 신규 브랜드 데이터 레이어

> **상태:** 세 절(구조·데이터 모델 / 콘텐츠 범위·집필 규칙 / 검증) 모두 사용자 승인 완료. 구현 플랜으로 넘어갈 수 있다.

## 배경

살림랩이 애드센스에서 "가치가 별로 없는 콘텐츠"로 거절됐다. 1순위였던 에러코드 통합(`2026-08-12-error-code-consolidation-design.md`)이 끝나 1,200자 미만 페이지가 279개(75%)에서 26개(20%)로 줄었다.

**남은 26개 중 15개가 `/brand/*`다.** 이제 이것이 얇은 페이지의 최대 덩어리다.

현재 브랜드 페이지는 헤더(브랜드명·제품 수·카테고리)와 제품 카드 그리드가 전부다.

| 브랜드 | 제품 | 페이지 길이 |
|---|---|---|
| LG · 삼성 | 20 · 17 | 2,288 · 1,985자 ✅ |
| 코웨이 ~ 로보락 (11개) | 2~6 | 492 ~ 912자 ❌ |
| 애플 · 소니 · 앤커 · QCY | 각 1 | 377 ~ 385자 ❌ |

## 결정 사항

- **17개 전부 보강한다.** 제품이 1개뿐인 4개(애플·소니·앤커·QCY)는 분량이 문턱에 걸칠 위험을 제기했으나, 사용자가 전부 살리기로 결정했다.
- **콘텐츠는 혼합형** — 데이터 파생 통계로 뼈대를 세우고 브랜드별 서술을 얹는다.
- **라인업 네이밍 체계를 중심 콘텐츠로 삼는다.**
- **통계는 저장하지 않고 파생한다.**
- **콘텐츠가 17개 다 차기 전에는 배포하지 않는다.**

### 왜 라인업 네이밍인가

브랜드 페이지가 제품 페이지·카테고리 페이지와 겹치지 않으려면 브랜드 레벨에만 존재하는 내용이어야 한다. 제품 스펙을 다시 늘어놓으면 그것은 내부 복제이고, 카테고리 페이지(6,004자)가 이미 하는 일이다.

브랜드 레벨에만 있는 것:

- **라인업 네이밍 체계** — 비스포크·그랑데·휘센·오브제컬렉션이 각각 무엇인지. "비스포크가 뭐야", "휘센이랑 오브제 차이" 같은 검색 수요가 실재하는데 현재 사이트 어디에도 없다.
- **A/S·서비스센터** — 브랜드별 대표번호와 보증. 실용적이고 검색량이 크다.
- **에러코드 체계의 특징** — 삼성은 `E+숫자`, LG는 문자 조합. 1순위에서 만든 허브로 연결된다.
- **라인업 통계** — 가격대 분포, 카테고리 커버리지, 에너지등급 분포. 파생이므로 집필 부담이 없고 중복도 아니다.

## 페이지 구조

```
LG                                    ← h1
제품 20개 · 11개 카테고리
[브랜드 소개 한 문단]

   휘센 — 에어컨 라인, ...

   카테고리 11개 · 가격 39만~349만원 · 평균 평점 4.3
   에너지등급 1등급 6 / 2등급 3 / 대상 아님 11

## 에러코드                            ← 브랜드 허브로 연결
   LG 제품에서 확인된 에러코드 57개 → 허브

   대표번호 ...

## 살림랩 총평                          ← 편집 관점 2~3문장

## 제품 20개                           ← 기존 카드 그리드

## 근거                                ← 출처 링크
```

## 데이터 모델

```ts
export interface BrandLine {
  name: string;                  // '비스포크'
  what: string;                  // 어떤 라인인지 1~2문장
  categories?: ApplianceCategory[];
}

export interface BrandProfile {
  brand: string;                 // 'Samsung' — BRAND_LABELS 키
  intro: string;                 // 사실 위주 소개 2~3문장
  lines: BrandLine[];
  serviceCenter?: { phone: string; sourceUrl: string; note?: string };
  errorCodePattern?: string;     // 에러코드 체계 특징
  editorNote: string;            // 살림랩 총평 2~3문장
  sources: SourceRef[];
  updated: string;               // 'YYYY-MM'
}
```

통계는 `allAppliances`에서 파생한다 — 제품이 추가되면 저절로 맞는다.

`serviceCenter`는 생략할 수 있지만, **쓰기로 했다면 `sourceUrl`이 반드시 따라온다.** "어떤 출처가 어떤 문장을 뒷받침하는가"는 일반적으로 코드가 알 수 없지만, A/S 번호만은 출처를 필드에 직접 묶어 검사 가능한 형태로 만든다. 틀린 번호가 실제 피해가 되는 유일한 항목이기 때문이다. `sourceUrl`은 `sources`의 어느 항목과 URL이 일치해야 한다.

### `SourceRef` 공용 타입 추출

성분 사전에서 `MaterialSource = { url, title, publisher? }`를 만들었고 브랜드도 같은 모양이 필요하다. **"출처는 발행처와 제목을 보인다"가 이제 사이트 전체의 편집 규칙**이므로 타입도 공용이 맞다.

`src/types/source.ts`에 `SourceRef`를 두고, `material.ts`는 그것을 import해 `MaterialSource`를 별칭으로 남긴다. 기존 코드는 건드리지 않는다.

## 분량 실측

현재 377자는 대부분 내비·푸터이고 제품 카드 하나가 약 90자를 더한다. 새 콘텐츠를 얹으면:

| 블록 | 예상 |
|---|---|
| 브랜드 소개 2~3문장 | ~150자 |
| 라인업 네이밍 2~4개 | ~250자 |
| 파생 통계 | ~120~200자 |
| 에러코드 요약 | ~100자 |
| A/S | ~80자 |
| 살림랩 총평 | ~150자 |

LG·삼성은 3,000자를 넘고, 중간 브랜드 11개는 1,500~2,000자로 안전하다.

**1개짜리 4개가 문제다.** 애플 기준 약 1,127자로 문턱에 걸린다. 카드가 하나뿐이고 통계도 성립하지 않는다. 300자 정도가 더 필요한데, 억지로 채우면 패딩이 된다.

**다만 이 넷은 쓸 것이 실제로 있다**: 카탈로그에 없는 라인업까지 포함한 체계 설명(에어팟 기본/프로/맥스의 차이), 그리고 **한국에서의 A/S 방식**(애플은 공인 서비스 제공업체, 소니·앤커는 수입사 경유). 둘 다 독자에게 실용적이고 다른 페이지에 없다.

## 집필 규칙

성분 사전에서 세운 규칙을 그대로 적용한다.

1. **근거 없는 우위 주장을 쓰지 않는다.** "국내 1위", "품질이 가장 좋은" 같은 문장은 출처가 없으면 마케팅 문구다. 시장 지위를 언급하려면 출처를 단다.
2. **라인업 이름은 제조사 공식 용어만 쓴다.** '비스포크'·'휘센'은 제조사 공식 명칭이고 공식 페이지가 출처가 된다. 통칭이나 커뮤니티 용어는 쓰지 않는다.
3. **A/S 번호는 제조사 공식 페이지에서 확인하고 출처를 단다.** 틀린 번호는 실제 피해가 된다. `serviceCenter.sourceUrl`로 강제한다.
4. **`editorNote`는 살림랩 관점이되 카탈로그 안의 제품에 근거한다.** "이 브랜드는 저가형이 약하다"가 아니라 "카탈로그의 3개 제품이 모두 프리미엄 가격대"처럼 검증 가능한 형태로 쓴다.
5. **`sources`가 빈 브랜드를 만들지 않는다** — 테스트로 강제한다.

## 비가전 브랜드 문구 수정

현재 메타데이터가 `${label} 가전 전체 — 스펙·가격 비교`다. **애플·소니·앤커·QCY에는 "가전"이 틀린 말이다.** 심사자가 "애플 가전"을 보면 사이트의 정확도를 의심한다.

판정은 브랜드명 목록이 아니라 데이터에서 파생한다: **브랜드의 제품이 하나도 `isTraditionalAppliance`가 아니면** "제품 전체"로 쓰고, 하나라도 가전이면 기존 문구를 유지한다. 지금은 넷 다 제품이 1개라 결과가 같지만, 규칙을 데이터에 걸어두면 나중에 브랜드나 제품이 늘어도 저절로 맞는다.

## 집필 순서

**대표 2개를 먼저 쓴다 — LG와 QCY.** 가장 큰 것과 가장 작은 것을 먼저 해야 구조가 양극단에서 성립하는지 확인된다. QCY가 1,200자를 못 넘으면 15개를 쓴 뒤에 아는 것보다 그때 설계를 고치는 편이 낫다.

그다음 나머지 15개를 3~4개씩 나눠 검수받는다. **AI가 17개를 한 번에 쏟아내지 않는다** — 그것이 구글이 말하는 대량 생성 패턴이고, 지금 거절당한 이유와 같은 부류다.

## 검증

### 1. 명령 순서

`npm run lint` → `npx tsc --noEmit` → `npm test` → `npm run build`

### 2. 분량 — 목표 지표

`scripts/measure-page-length.mjs`를 만든다. 경로 글롭과 임계값을 인자로 받아 `out/`의 HTML을 본문 텍스트로 환산하고, 페이지별 글자 수와 미달 개수를 출력한다.

이전 사이클은 같은 측정을 플랜 본문에 박아둔 node 한 줄로 했다. 이번엔 집필이 "LG·QCY 먼저 → 3~4개씩 여러 라운드"라 같은 측정을 열 번 넘게 반복하고, 다음 사이클 셋(리뷰·성분 본문·홈)도 같은 지표를 쓴다. 손으로 옮겨 붙이면 라운드마다 다른 것을 재게 된다.

합격선: `/brand/*` 17개가 전부 1,200자 이상.

**QCY 게이트** — LG·QCY 둘만 먼저 쓰고 즉시 측정한다. QCY가 1,200자를 못 넘으면 **나머지 15개를 쓰기 전에** 구조를 고친다. 15개를 다 쓴 뒤에 알게 되는 것을 피하는 것이 이 집필 순서의 목적이므로, 판정 지점을 여기 못 박는다.

### 3. 데이터 무결성 (vitest)

- **커버리지 진행률** — `getAllBrands()`의 17개 중 `BrandProfile`이 없는 브랜드를 **전부 이름으로 출력하며** 실패하는 테스트 하나. 집필이 끝날 때까지 이 테스트는 계속 실패하는데, 실패가 하나뿐이고 메시지가 남은 할 일 목록이므로 새로 생긴 고장과 구분된다. "17개가 다 차기 전에는 배포하지 않는다"는 결정과 같은 것을 말한다.
- `sources`가 비어 있지 않고 `url`이 `http(s)`, `title`이 채워져 있다
- `lines[].categories`가 실재하는 `ApplianceCategory`다
- `serviceCenter.sourceUrl`이 `sources`의 어느 `url`과 정확히 일치한다
- `updated`가 `YYYY-MM` 형식이다

### 4. 브랜드 간 중복

17개의 `intro`·`lines[].what`·`editorNote`를 서로 대조한다. 공백 정규화 후 **문장 단위 완전 일치가 1건이라도 있으면 실패**. 더불어 겹침이 큰 쌍을 순위로 출력해 검수 때 사람이 본다.

원래 계획은 브랜드 페이지를 제품·카테고리 페이지와 대조하는 것이었으나, 브랜드명·카테고리명·제품명이 설계상 양쪽에 나오므로 임계값 없이는 항상 걸리거나 항상 통과한다. 실제 위험은 다른 곳에 있다 — "AI가 17개를 한 번에 쏟아내지 않는다"가 경계하는 실패는 17개 서술이 서로 붕어빵이 되는 것이고, 그것은 빌드 산출물 없이 데이터만으로 검사된다. 카테고리 페이지와의 겹침은 자동화하지 않고 LG·QCY 검수 때 한 번 눈으로 본다.

**유사도에 고정 임계값을 걸지 않는 이유**: 집필 규칙 4번("카탈로그의 3개 제품이 모두 프리미엄 가격대"처럼 검증 가능하게)은 `editorNote`를 의도적으로 정형문에 가깝게 만든다. n-gram 임계값을 걸면 규칙 4를 지킬수록 테스트가 깨진다. 문장 완전 일치만 하드 페일로 두고 유사도 판단은 사람에게 넘긴다.

### 5. 비가전 문구

브랜드 목록을 하드코딩하지 않고 `allAppliances`에서 비가전 전용 브랜드를 뽑아, 그 브랜드들의 메타데이터 title·description에 "가전"이 없는지 테스트한다. 지금은 애플·소니·앤커·QCY 넷이 걸리고, 나중에 비가전 브랜드가 추가돼도 저절로 걸린다.

### 6. 회귀

제품 74개·에러코드 허브 13개 유지, 사이트맵 URL 수 변화 없음.
